## 1. Resumen ejecutivo

Portik es una plataforma web para control de acceso, operación de portería y administración básica de conjuntos residenciales, condominios y comunidades cerradas.

El producto busca resolver un problema común en conjuntos residenciales: la operación diaria depende de llamadas, mensajes, hojas de cálculo, papel, memoria del personal de portería y procesos poco trazables.

Portik centraliza la información operativa del conjunto para que administración, portería y residentes puedan trabajar con mayor orden, control y trazabilidad.

La prioridad comercial de Portik debe ser validar un piloto real con administradores de condominios o conjuntos residenciales, enfocándose primero en portería, control de visitantes, predios, vehículos, novedades, reservas y bitácora.

---

## 2. Posicionamiento comercial

Portik debe presentarse como:

> Una plataforma web que ayuda a conjuntos residenciales a controlar visitantes, vehículos, reservas, novedades y operación de portería desde un solo lugar, reduciendo llamadas, errores y falta de trazabilidad.

No debe venderse inicialmente como:

- App móvil completa.
- Sistema contable.
- Sistema de pagos.
- Solución de hardware.
- Reconocimiento automático de placas.
- ERP para administración inmobiliaria.
- Plataforma de seguridad física avanzada.

El enfoque inicial es:

> Ordenar y controlar la operación diaria del conjunto, especialmente en portería y administración.

---

## 3. Cliente ideal

Portik debe dirigirse inicialmente a:

| Cliente ideal | Motivo |
|---|---|
| Administradores de condominios | Tienen dolor operativo diario y capacidad de decisión |
| Empresas administradoras de propiedades | Pueden escalar el producto a varios conjuntos |
| Juntas directivas de conjuntos residenciales | Tienen interés en control, trazabilidad y transparencia |
| Conjuntos con portería física | Tienen flujo constante de visitantes y vehículos |
| Conjuntos con reservas de áreas comunes | Necesitan reglas, control y calendario |
| Residenciales con problemas de comunicación | Pueden beneficiarse de notificaciones internas y autogestión |

Cliente no ideal para la primera etapa:

- Edificios muy pequeños sin presupuesto.
- Comunidades sin portería.
- Clientes que exigen app móvil nativa desde el primer día.
- Clientes que exigen pagos en línea como requisito principal.
- Clientes que solo buscan cámaras, hardware u OCR.
- Administraciones sin disposición a ordenar datos maestros.

## 4. Problema que resuelve

Los conjuntos residenciales suelen operar con información dispersa entre:

- WhatsApp.
- Hojas de cálculo.
- Llamadas.
- Cuadernos de portería.
- Archivos físicos.
- Memoria del personal.
- Correos aislados.
- Sistemas incompletos.

Esto genera:

| Problema | Impacto |
|---|---|
| Portería no tiene información clara | Demoras y decisiones inconsistentes |
| No hay trazabilidad de ingresos y salidas | Dificultad para auditar eventos |
| Visitantes y vehículos se autorizan informalmente | Riesgo operativo |
| Administración recibe llamadas repetitivas | Pérdida de tiempo |
| Reservas de áreas comunes se manejan manualmente | Conflictos y errores |
| Novedades no quedan registradas correctamente | Falta de seguimiento |
| Cada conjunto aplica reglas distintas | Desorden operativo |
| Los residentes dependen de llamadas o mensajes | Mala experiencia |

---

## 5. Propuesta de valor

La propuesta de valor de Portik es:

> Portik permite que administración, portería y residentes trabajen con una fuente única de información para controlar accesos, autorizaciones, parqueaderos, reservas, novedades y bitácora operativa del conjunto.

Resultados esperados:

- Menos llamadas entre portería y administración.
- Menos errores al validar visitantes.
- Mayor trazabilidad de ingresos y salidas.
- Mejor control de vehículos y parqueaderos.
- Administración más ordenada.
- Mejor experiencia para residentes.
- Reportes básicos disponibles cuando se necesiten.
- Reglas operativas claras por conjunto.
- Menor dependencia de hojas de cálculo o cuadernos.

## 6. Mensaje comercial corto

### Versión de 15 segundos

> Portik ayuda a conjuntos residenciales a controlar visitantes, vehículos, reservas y novedades desde una plataforma web, para que portería y administración trabajen con más orden y trazabilidad.

### Versión de 30 segundos

> Muchos conjuntos todavía manejan autorizaciones, visitantes, parqueaderos y reservas con llamadas, WhatsApp, Excel o cuadernos. Portik centraliza esa operación en una plataforma web para que portería pueda consultar rápido, administración tenga trazabilidad y los residentes puedan autogestionar solicitudes básicas.

### Versión consultiva

> Portik no reemplaza la administración del conjunto; la ordena. El objetivo es que portería tenga la información correcta en el momento correcto, que administración pueda configurar reglas y revisar trazabilidad, y que el residente pueda hacer solicitudes simples sin depender siempre de llamadas o mensajes.

## 7. Alcance comercial del piloto

El piloto de Portik debe ser limitado, claro y vendible.

### Incluido en piloto

| Módulo | Incluido |
|---|---|
| Configuración inicial | Crear conjunto, estructura, usuarios y roles |
| Predios | Cargar predios, torres, bloques o etapas |
| Personas | Propietarios, residentes o contactos autorizados |
| Vehículos | Vehículos asociados a predios |
| Portería | Búsqueda por placa y predio |

| Ingresos/salidas | Registro manual de eventos |
| Parqueaderos | Ocupación y liberación de visitantes |
| Novedades | Registro y consulta básica |
| Reservas | Áreas comunes y calendario básico |
| Bitácora | Trazabilidad de acciones relevantes |
| Reportes | Consultas simples y exportación CSV |
| Capacitación | Sesión básica para administración y portería |
| Soporte | Soporte durante el piloto |

### Fuera del piloto

- App móvil nativa.
- Pagos en línea.
- Integración con pasarelas de pago.
- Reconocimiento automático de placas.
- Cámaras o hardware.
- OCR.
- WhatsApp automático.
- Correo automático avanzado.
- Firma electrónica.
- Integración contable.
- Integración con ERP.
- Reportes analíticos avanzados.
- Exportación PDF/Excel avanzada.
- Migraciones complejas desde sistemas externos.

**Portik Piloto Operativo**

### Objetivo

Validar Portik en un conjunto real durante un período controlado, midiendo su utilidad para administración, portería y residentes.

### Duración sugerida

30 a 60 días.

### Entregables

- Configuración de 1 conjunto.
- Usuarios administrativos.
- Usuarios de portería.
- Carga inicial de datos básicos.
- Flujo de búsqueda por placa.
- Flujo de búsqueda por predio.
- Registro de ingresos y salidas.
- Registro de parqueaderos.
- Gestión básica de reservas.
- Bitácora.
- Capacitación inicial.
- Soporte del piloto.
- Informe de hallazgos y mejoras al cierre.

### Modelo de cobro sugerido

Opción A — Piloto pagado:

- Pago inicial de configuración.
- Mensualidad reducida durante el piloto.
- Conversión a plan mensual completo al finalizar.

Opción B — Piloto semi-pagado:

- Pago de configuración obligatorio.
- Mensualidad bonificada o reducida.
- Compromiso de feedback y testimonio anonimizado si el piloto funciona.

No se recomienda piloto completamente gratis, salvo que exista un beneficio comercial claro, como acceso a varios conjuntos o una referencia estratégica.

## 9. Guion de demo comercial

La demo debe durar entre 15 y 25 minutos.

### 9.1 Apertura

Objetivo: conectar con el dolor del cliente.

Mensaje sugerido:

> La idea de esta demo es mostrar cómo un conjunto puede organizar la operación diaria de portería y administración sin depender tanto de llamadas, WhatsApp, Excel o cuadernos. Nos vamos a enfocar en visitantes, vehículos, predios, parqueaderos, reservas, novedades y trazabilidad.

Preguntas iniciales:

- ¿Cómo autorizan visitantes actualmente?
- ¿Cómo sabe portería si un predio tiene restricciones?
- ¿Dónde registran ingresos y salidas?
- ¿Cómo manejan parqueaderos de visitantes?
- ¿Cómo manejan reservas de áreas comunes?
- ¿Qué ocurre cuando hay una novedad o incidente?

---

### 9.2 Escenario 1 — Consulta por placa

Objetivo: mostrar rapidez operativa para portería.

Flujo:

1. Entrar como usuario de portería.
2. Buscar una placa.
3. Mostrar predio asociado.
4. Mostrar estado operativo.
5. Mostrar restricciones o alertas visibles.
6. Mostrar si tiene autorización activa.
7. Registrar ingreso.
8. Registrar salida.

Mensaje de valor:

> Portería no necesita llamar a administración para cada validación básica. Puede consultar la información operativa necesaria en segundos y dejar trazabilidad.

---

### 9.3 Escenario 2 — Consulta por predio

Objetivo: mostrar ficha operativa del predio.

Flujo:

1. Buscar un predio.
2. Mostrar propietarios o contactos autorizados.
3. Mostrar vehículos.
4. Mostrar estado operativo.
5. Mostrar alertas o restricciones.
6. Mostrar reservas próximas.
7. Mostrar novedades activas.

Mensaje de valor:

> La ficha del predio funciona como una fuente única de verdad operativa para portería.

---

### 9.4 Escenario 3 — Registro de visitante

Objetivo: mostrar control de acceso manual pero trazable.

Flujo:

1. Seleccionar predio.
2. Registrar visitante.
3. Asociar autorización o ingreso.
4. Confirmar datos mínimos.
5. Guardar evento.
6. Mostrar evento en historial o bitácora.

Mensaje de valor:

> Aunque el ingreso sea manual, el conjunto gana trazabilidad y reduce dependencia del cuaderno físico.

---

### 9.5 Escenario 4 — Parqueadero visitante

Objetivo: mostrar control operativo de cupos.

Flujo:

1. Validar si el visitante requiere parqueadero.
2. Asignar cupo.
3. Registrar hora de ocupación.
4. Liberar cupo al salir.
5. Mostrar estado del parqueadero.

Mensaje de valor:

> Administración puede controlar ocupación y uso de parqueaderos de visitantes con mayor claridad.

---

### 9.6 Escenario 5 — Reserva de zona común

Objetivo: mostrar reglas y autogestión básica.

Flujo:

1. Entrar como administración o residente.
2. Consultar calendario.
3. Crear solicitud de reserva.
4. Validar reglas.
5. Aprobar o rechazar según configuración.
6. Mostrar reserva activa.

Mensaje de valor:

> Las reservas dejan de depender de mensajes aislados y pasan a un calendario con reglas y trazabilidad.

---

### 9.7 Escenario 6 — Bitácora y reportes

Objetivo: mostrar valor administrativo.

Flujo:

1. Entrar como administración.
2. Consultar bitácora.
3. Filtrar por fechas, usuarios o eventos.
4. Consultar registros de acceso.
5. Exportar CSV simple.

Mensaje de valor:

> La administración puede revisar qué ocurrió, cuándo ocurrió y quién realizó cada acción.

## 11. Objeciones y respuestas

| Objeción | Respuesta recomendada |
|---|---|
| “Ya usamos WhatsApp” | WhatsApp sirve para comunicación, pero no para trazabilidad, permisos, reportes ni control operativo. Portik no elimina WhatsApp; reduce la dependencia de mensajes dispersos. |
| “La portería no es muy tecnológica” | El flujo de portería debe ser simple: buscar placa, ver ficha, registrar ingreso o salida. La demo se enfoca en pocos clics. |
| “No queremos app móvil todavía” | Perfecto. El MVP es web, más fácil de implementar y mantener. La app móvil puede evaluarse después si el piloto demuestra valor. |
| “Queremos reconocimiento de placas” | Se puede considerar en una fase futura. Primero conviene ordenar datos, reglas y trazabilidad; luego se justifica hardware u OCR. |
| “Eso suena costoso” | El piloto permite validar valor con alcance controlado antes de invertir en módulos avanzados. |
| “Tenemos muchos datos en Excel” | Se puede hacer una carga inicial básica, siempre que los datos estén ordenados. La limpieza profunda se cotiza aparte. |
| “Necesitamos pagos en línea” | Pagos puede ser una fase posterior. El primer objetivo es controlar operación, accesos, reservas y trazabilidad. |

Antes de una demo comercial:

- Usar solo datos ficticios.

- Tener usuarios de prueba listos.
- Confirmar que el flujo de login funciona.
- Confirmar búsqueda por placa.
- Confirmar búsqueda por predio.
- Confirmar registro de ingreso.

## 16. Próximo paso después de la demo

Al finalizar una demo, no cerrar con “me avisas”.

Cerrar con una decisión concreta:

> Si esto les hace sentido, el siguiente paso sería hacer un diagnóstico corto de su operación actual, revisar cuántos predios tienen, cómo manejan visitantes y qué datos tienen disponibles. Con eso les preparo una propuesta de piloto con alcance, tiempo y costo.

Acción concreta:

- Agendar diagnóstico.
- Pedir ejemplo de estructura de predios.
- Confirmar usuarios clave.
- Confirmar dolor principal.
- Enviar propuesta de piloto.

## 17. Decisiones recomendadas

1. Portik debe ser el producto principal de validación comercial inmediata.
2. El piloto debe limitarse a operación de portería, administración básica, reservas, parqueaderos y bitácora.
3. No se deben incluir pagos, hardware, OCR ni app móvil nativa en el piloto.
4. La demo debe enfocarse en rapidez, trazabilidad y reducción de llamadas.
5. El primer objetivo no es vender a muchos conjuntos, sino cerrar un piloto que genere aprendizaje, caso de éxito y mensualidad.
